🇬🇧 [In English](CONTRIBUTING.md)

## 1. Выберите вид вклада

| Я хочу... | Что делать |
|---|---|
| рассказать об ошибке и о том, как я её победил | [создать issue](../../issues/new?template=new-error.yml), см. [раздел 2](#2-способ-за-5-минут-сообщить-об-ошибке) |
| сообщить, что сигнатура срабатывает зря | [создать issue](../../issues/new?template=signature-problem.yml); лучше добавить негативную фикстуру в pull request |
| написать новую сигнатуру | [раздел 3](#3-написать-сигнатуру-по-шагам) |
| добавить фикстуры к существующей сигнатуре | положите логи в `kb/fixtures/SIG-XX-000/` и перечислите их в `tests:` этой сигнатуры |
| улучшить текст сигнатуры | поправьте YAML, увеличьте `version` на 1 |
| поправить документацию | измените файл и откройте pull request |

Чтобы помочь, писать сигнатуры **не обязательно**: хороший issue с очищенным логом и источником, объясняющим ошибку, уже половина работы, остальное допишет мейнтейнер.

**Язык.** Текст сигнатуры (`title`, `symptoms`, `cause`, `fix`) показывается владельцам серверов в боте, сейчас он русскоязычный. Пишите по-русски или по-английски, мейнтейнеры переведут. Issue и pull request можно вести на любом из двух языков.

## 2. Способ за 5 минут: сообщить об ошибке

Заполните [форму новой ошибки](../../issues/new?template=new-error.yml). В ней спрашивают платформу, плагин, очищенный фрагмент лога и причину, если вы её знаете. Лучшее доказательство причины — ссылка: на исходники плагина, issue в его репозитории или официальную документацию.

## 3. Написать сигнатуру по шагам

Нужны Java 21, Git и текстовый редактор. Один раз скачайте валидатор:

```bash
# из релиза "tools" этого репозитория
unzip kb-tools.zip          # получится kb-tools-<версия>/bin/kb-tools (на Windows kb-tools.bat)
```

### Шаг 1. Разберитесь, почему ошибка возникает

Найдите **первоисточники**: исходники плагина, где печатается сообщение, issue в его репозитории, документацию серверного ПО. Их вы перечислите в `sources:`. Сигнатуру без источников не примут: «у меня сработало» — подсказка, а не доказательство.

### Шаг 2. Возьмите лог и очистите его

Возьмите фрагмент `latest.log` с ошибкой: строку, её stack trace и 10-30 строк вокруг. Затем **удалите персональные данные** (раздел 4). Валидатор сделает большую часть за вас:

```bash
kb-tools sanitize --in latest.log --out kb/fixtures/SIG-DB-099/pos-my-case.log \
  --grep "Communications link failure" --context 30
```

После этого прочитайте результат сами.

### Шаг 3. Выберите id и категорию

Id имеет вид `SIG-<ПРЕФИКС>-<номер>`, файл лежит в папке своей категории:

| Категория (папка) | Префикс | Что сюда относится |
|---|---|---|
| `auth` | `AU` | авторизация игроков, сессия Mojang, forwarding-секреты |
| `database` | `DB` | соединения с MySQL/MariaDB/Redis, пулы, права |
| `disk` | `DI` | место на диске, ошибки ввода-вывода, права доступа |
| `memory` | `MEM` | OutOfMemory, GC, heap, нативная память |
| `network` | `NW` | порты, DNS, TLS, таймауты между серверами |
| `performance` | `PA` | лаги, время тика, watchdog |
| `plugin` | `PL` | плагин не загрузился или не включился, зависимости, версии API |
| `startup` | `ST` | сервер не стартует, версия Java, флаги |
| `velocity` | `VE` | прокси и его backend'ы |
| `world` | `WO` | мир, чанки, region-файлы, датапаки |

Возьмите следующий свободный номер в категории (посмотрите папку). Если двое взяли один номер, мейнтейнер перенумерует один из них при мердже, не переживайте.

### Шаг 4. Напишите файл сигнатуры

Скопируйте [`docs/templates/signature.yml`](docs/templates/signature.yml) в `kb/signatures/<категория>/SIG-XX-NNN.yml` (имя файла должно совпадать с `id`) и заполните. Главные правила:

- **`verification: candidate`** для новой сигнатуры. Повысят её мейнтейнеры после ревью.
- **`match` должен опираться на лог.** Нужен хотя бы один предикат `log`. Задайте каждому `log` поле `literal` от 8 символов: это быстрый префильтр, регулярка запускается только на строках, где он найден.
- **Будьте точны.** Привяжите регулярку к классу исключения, имени плагина или литералу от 16 символов. Просто «Error» или «Exception» сработает на половине интернета.
- **`action: null`.** Tickwise не выполняет команды на серверах; сигнатура только объясняет и советует.
- **`fix.instructions_md`** — нумерованные шаги, которым уставший админ последует в три часа ночи. Первая строка показывается в краткой форме, сделайте её содержательной. Не просите присылать конфиг целиком: в нём бывают пароли.
- **`sources`** — ссылки из шага 1.

Полный справочник полей — в [docs/writing-signatures.ru.md](docs/writing-signatures.ru.md).

### Шаг 5. Напишите фикстуры

Для каждой сигнатуры нужно **не меньше трёх позитивных и трёх негативных** фикстур в `kb/fixtures/<ID>/`:

- `pos-<описание>.log`: сигнатура **обязана** сработать. Меняйте, что можно: другой плагин, другая платформа (Paper и Velocity), другой драйвер, другая формулировка той же ошибки.
- `neg-<описание>.log`: сигнатура **обязана молчать**. Полезнее всего негативные «двойники»: то же слово в обычной INFO-строке, другая причина похожей ошибки, соседний тип исключения. Именно они ловят слишком широкую регулярку.

В начале каждой фикстуры пишите заголовок и честно указывайте происхождение:

```
# platform: paper 1.21.11
# plugins: LuckPerms 5.5.17
# source: собственный сервер, очищено (2026-10-04)
[09:20:00] [ForkJoinPool.commonPool-worker-3/WARN]: ...
```

`source:` — это `synthetic` (лог вы собрали руками по настоящему формату сообщения), `upstream-issue <url>` или описание вашего сервера. Синтетические фикстуры допустимы, но сигнатура, у которой позитивные фикстуры только синтетические, получит максимум `community`.

### Шаг 6. Проверьте

```bash
kb-tools/bin/kb-tools test --kb kb
bash scripts/lint-fixtures.sh
```

Нужны `KB TEST PASSED` и `Privacy lint passed.` Тест прогоняет **каждую** сигнатуру по **каждой** фикстуре репозитория, поэтому он же покажет, если ваша сигнатура срабатывает на чужом логе или чужая на вашем. Исправьте это, сделав регулярку точнее, либо добавьте нужный id в заголовок фикстуры `# expect:` (только если сработать должны обе сигнатуры).

## 4. Настоящие логи и приватность

В логе много такого, что публиковать нельзя. Прежде чем лог станет фикстурой, **вы** обязаны убрать:

| Убрать | Заменить на |
|---|---|
| ники и UUID игроков | `Player`, `Steve`, `00000000-0000-0000-0000-000000000000` |
| IP-адреса (игроков, вашего сервера, вашей БД) | `203.0.113.5` (документационный диапазон) или `10.0.0.5` |
| ваши домены и хосты | `db.example.net`, `play.example.com` |
| e-mail | `user@example.com` |
| пароли, токены, ключи, webhook'и, RCON | удалить значение или написать `<redacted>` |
| абсолютные пути с именем пользователя | `/home/minecraft/...` |
| сообщения игроков в чате | удалить строки |

`kb-tools sanitize` делает большую часть этого, а CI-проверка приватности ловит типичные утечки (похожие на настоящие IP, e-mail, секреты). Это страховка, **не гарантия**, поэтому прочитайте фикстуру построчно. Если после мерджа вы нашли просочившийся ник, напишите нам в личные сообщения, и мы перепишем историю.

Используйте только логи серверов, которыми **вы владеете или которые администрируете**, либо публичные issue с логами их владельцев. Не присылайте логи чужого сервера без разрешения его владельца.

## 5. Откройте pull request

1. Сделайте fork и создайте ветку: `signature/db-pool-timeout` или `fixtures/sig-db-001`.
2. Коммиты: один логический набор изменений на pull request проверять проще всего. Сообщение вроде `signature: SIG-DB-099 Hikari pool timeout` — то, что нужно.
3. **Не трогайте** `kb/pack.yml` и не добавляйте `kb/dist/`: это зона мейнтейнеров, потому что pack подписывается.
4. Откройте pull request и заполните шаблон.
5. CI запускает две проверки: приватность и полный прогон фикстур. Красные проверки исправляйте в той же ветке, PR обновится сам.

## 6. На что смотрит ревью

- **Верна ли причина** и подтверждена ли она первоисточником?
- **Достаточно ли узкая сигнатура?** Смотрим на регулярку и на ваши негативные фикстуры.
- **Честные ли фикстуры,** очищены ли они, покрывают ли разные варианты?
- **Безопасен ли и полезен совет?** Шаги, рискующие потерей данных или требующие `chmod 777`, отклоняются.
- **Понятен ли текст** неспециалисту?

Ждите замечаний: это нормально и значит, что вашу работу читают. Стараемся отвечать в течение нескольких дней.

## 7. Что даёт доступ к бете

Мейнтейнер ставит метку **`beta-access`** при мердже вклада, который делает Tickwise лучше. Ориентир: обычно её дают за

- новую сигнатуру с фикстурами 3+3, первоисточниками и реальной повторяющейся ошибкой;
- исправление ложного срабатывания или пропуска вместе с фикстурами, которые это доказывают;
- набор полезных фикстур, показывающих настоящие дыры в существующих сигнатурах;
- существенное улучшение документации или перевод.

Это принимается, но метку само по себе обычно **не** даёт: правки опечаток и форматирования, пробелы, переименования, дубли существующих сигнатур, изменения без тестов и источников. Непроверенные сгенерированные pull request закрываются. Пользоваться ассистентом можно, если причину, источники и фикстуры вы проверили сами.

Решение за мейнтейнером. Если ваш PR смержен без метки и вы считаете, что она нужна, вежливо спросите в комментариях.

Один GitHub-аккаунт получает один грант, один аккаунт мессенджера держит один грант. Доступ личный и не передаётся, при злоупотреблении его могут отозвать. SLA нет: бета остаётся бетой.

## 8. После мерджа

Если на PR есть метка `beta-access`, получите доступ в боте Tickwise:

1. `/beta github` (в Discord: `/tickwise beta github`). Бот покажет ссылку и код.
2. Откройте ссылку, введите код и подтвердите на GitHub. **Права не запрашиваются.**
3. `/beta check`. Бот подтвердит, и вы сможете привязывать серверы командой `/link`.

Код действует 15 минут; если он истёк, начните заново. Tickwise читает id и логин вашего GitHub-аккаунта, ищет в этом репозитории ваш смердженный PR с меткой и сразу забывает токен GitHub.

Ваша сигнатура попадёт к пользователям в следующем **подписанном pack**: мейнтейнер перенесёт её в приватный репозиторий и подпишет сборку. Это может занять несколько дней.

## 9. Если что-то не получается

| Проблема | Что делать |
|---|---|
| `Privacy lint failed` | прочитайте перечисленные строки; замените IP, e-mail, секреты, как в разделе 4 |
| `precision` ниже нужной или в выводе `FALSE-POSITIVE` | ваша сигнатура срабатывает на логе, где не должна, или чужая срабатывает на вашей фикстуре. Сузьте регулярку, добавьте `literal` или `# expect:`, если правы обе |
| `signature X has fewer than 3 positive/negative fixtures` | добавьте фикстуры и перечислите их в `tests:` |
| ошибка про отсутствие `log`-предиката (доказательства) | в дереве `match` нужен `log`, который обязан быть истинным. `not` доказательством не считается |
| регулярка «невалидна» | движок RE2: нет backreference, нет lookahead и lookbehind |
| фикстура не совпадает, хотя лог выглядит верно | валидатор сопоставляет **санитизированный** текст: ники, IP и хосты уже заменены на заглушки вроде `<ip:1a2b3c4d>` или `<secret:high_entropy>` |
| `/beta check` отвечает «нет смердженного PR с меткой» | PR не смержен, на нём ещё нет метки `beta-access` или он открыт с другого GitHub-аккаунта |
| что-то другое | откройте issue, поможем |

## 10. Правила

- Будьте доброжелательны. См. [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
- Вы должны иметь право присылать то, что присылаете. Открывая pull request, вы соглашаетесь, что он публикуется по [лицензии](LICENSE) репозитория.
- Проблемы безопасности: [SECURITY.md](SECURITY.md), не публичный issue.
