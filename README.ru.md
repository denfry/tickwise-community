# Tickwise Community

**Помогите администраторам Minecraft-серверов чинить ошибки быстрее и получите ранний доступ к закрытой бете Tickwise.**

🇬🇧 [Read in English](README.md)

[Tickwise](https://tickwise.politernal.ru) — помощник по диагностике Minecraft-серверов и сетей (Paper, Purpur, Velocity). Небольшой плагин читает лог сервера и **локально** узнаёт известные проблемы по подписанной базе знаний. Если владелец привязал сервер, плагин отправляет в облако санитизированные данные. Облако превращает их в одно понятное сообщение в Telegram или Discord: что сломалось, почему и что делать.

Качество этого сообщения зависит от базы знаний, то есть от **сигнатур ошибок**. Сообщество пишет их в этом репозитории.

> Tickwise в **закрытой бете**. Принятый вклад сюда — один из способов попасть в бету, см. [Как получить доступ к бете](#как-получить-доступ-к-бете).

## Что такое сигнатура

Сигнатура — небольшое декларативное правило (YAML-файл): *«если в логе есть такая ошибка, причина — X, исправление — Y»*. Кода в ней нет: только регулярные выражения, условия и текст, который прочитает владелец сервера.

```yaml
id: SIG-DB-001
title: "База данных недоступна (MySQL: Communications link failure / MariaDB: Socket fail to connect)"
match:
  log:
    regex: 'Socket fail to connect to \S+'
    literal: "Socket fail to connect to"
cause: "Драйвер JDBC не смог установить TCP-соединение с сервером БД: ..."
fix:
  instructions_md: |
    1. Посмотрите хвост сообщения в evidence: `Connection refused` — на адресе никто не слушает ...
```

Каждая сигнатура подтверждена **фикстурами** — фрагментами логов: не меньше трёх, где она обязана сработать, и трёх похожих, где она обязана молчать. Тест прогоняет их все на каждом pull request, поэтому неверная сигнатура не пройдёт.

Сейчас в базе **42 сигнатуры и 280 фикстур**: базы данных, плагины, память, производительность, запуск, forwarding Velocity и другое. Настоящие примеры лежат в [`kb/signatures/`](kb/signatures).

## Чем можно помочь

| Вклад | Время | Подходит |
|---|---|---|
| **Сообщить об ошибке без сигнатуры** ([форма](../../issues/new?template=new-error.yml)) | 5 минут | тем, кто увидел ошибку и нашёл решение |
| **Добавить фикстуры** к существующей сигнатуре | 15 минут | тем, кто нашёл лог, где сигнатура срабатывает зря или молчит |
| **Написать новую сигнатуру** | 1-3 часа | авторам плагинов, админам, победившим неприятную проблему |
| **Улучшить формулировку или шаги** сигнатуры | 10 минут | тем, кто проверил исправление и знает способ лучше |
| **Поправить документацию** | любое | тем, кто застрял при чтении |

Начните с [CONTRIBUTING.ru.md](CONTRIBUTING.ru.md). Полный формат сигнатуры — в [docs/writing-signatures.ru.md](docs/writing-signatures.ru.md).

## Как получить доступ к бете

Tickwise в закрытой бете. Войти можно любой из дверей:

1. **Вклад.** Откройте pull request сюда. Когда мейнтейнер смерджит его **и поставит метку `beta-access`**, ключом станет ваш GitHub-аккаунт:
   1. В боте Tickwise отправьте `/beta github` (в Discord: `/tickwise beta github`).
   2. Откройте ссылку, введите код, который показал бот, и подтвердите. GitHub **не запрашивает прав**: Tickwise читает только id и логин аккаунта.
   3. Отправьте боту `/beta check`. Готово, можно привязывать серверы.
2. **Инвайт-код.** Если мейнтейнер дал код вида `TW-XXXX-XXXX`, отправьте `/beta code TW-XXXX-XXXX`.
3. **Попросить.** Не все пишут код. Расскажите о своём сервере на сайте.

Метку получает не каждый смердженный PR: исправленная опечатка нам очень приятна и принимается, но метка — за вклад, который делает Tickwise лучше, например проверенная сигнатура с фикстурами. Подробности — в [CONTRIBUTING.ru.md](CONTRIBUTING.ru.md#7-что-даёт-доступ-к-бете).

## Что происходит с вашим вкладом

1. Вы открываете pull request. Робот проверяет формат, прогоняет все фикстуры и ищет персональные данные.
2. Мейнтейнер делает ревью: проверяет причину, источники и что сигнатура не слишком широкая.
3. После мерджа мейнтейнер переносит принятое в приватный репозиторий Tickwise, повышает версию, собирает **Signature Pack** и **подписывает его офлайн**.
4. Агенты скачивают подписанный pack и проверяют подпись. Сигнатура из этого репозитория **не попадёт на сервер без такого ревью и подписи**, а новые сигнатуры сообщества начинают с низшего уровня доверия (`candidate` / `community`).

Поэтому вклад не может сломать чужой сервер, а сам по себе pull request для пользователей ничего не меняет.

## Устройство репозитория

| Путь | Что это |
|---|---|
| `kb/signatures/<категория>/SIG-XX-000.yml` | одна сигнатура на файл |
| `kb/fixtures/SIG-XX-000/pos-*.log`, `neg-*.log` | фикстуры: обязана сработать / обязана молчать |
| `kb/config-schema.yml` | какие ключи конфигов агент вправе читать |
| `kb/pack.yml` | метаданные pack, **только мейнтейнеры** |
| `docs/writing-signatures.ru.md` | полный формат и правила качества |
| `scripts/lint-fixtures.sh` | проверка на персональные данные (её запускает CI) |
| `tools/` | контрольная сумма валидатора, который скачивает CI |

## Проверка у себя

Нужна Java 21. Скачайте `kb-tools.zip` из [релиза `tools`](../../releases/tag/tools), распакуйте и запустите:

```bash
kb-tools/bin/kb-tools test --kb kb         # на Windows: kb-tools\bin\kb-tools.bat
bash scripts/lint-fixtures.sh              # проверка на персональные данные
```

Должно быть `KB TEST PASSED`. CI запускает те же две команды.
