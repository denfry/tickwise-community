# Как писать сигнатуры

Справочник по формату сигнатур, фикстур и проверкам. Пошаговое руководство для первого вклада — [CONTRIBUTING.ru.md](../CONTRIBUTING.ru.md). Шаблон файла — [`templates/signature.yml`](templates/signature.yml).

🇬🇧 [English version](writing-signatures.md)

Сигнатура — декларативное правило: RE2-регулярки и предикаты плюс текст причины и исправления. Агент исполняет сигнатуры локально, облако берёт из подписанного pack заголовок, причину и шаги для карточек инцидентов. Код в сигнатуре исполнить нельзя: только данные.

## 1. Раскладка

```
kb/
  signatures/<категория>/SIG-XX-000.yml     одна сигнатура на файл
  fixtures/SIG-XX-000/pos-*.log, neg-*.log  фикстуры
  config-schema.yml                          allowlist конфиг-ключей (меняют мейнтейнеры)
  pack.yml                                   метаданные pack (только мейнтейнеры)
```

Собранный и подписанный pack (`kb/dist/`) хранится в приватном репозитории Tickwise: подпись ставится офлайн на машине мейнтейнера, поэтому pull request его не затрагивает.

## 2. Инструмент `kb-tools`

Скачайте `kb-tools.zip` из [релиза `tools`](../../../releases/tag/tools), распакуйте. Нужна Java 21. Запуск: `kb-tools-<версия>/bin/kb-tools <команда> [--опция значение]...` (на Windows `kb-tools.bat`). У каждой опции должно быть значение: флагов без значения нет.

| Команда | Что делает |
|---|---|
| `validate --kb kb` | схема и RE2 каждой сигнатуры, наличие ≥ 3 позитивных и ≥ 3 негативных фикстур |
| `test --kb kb` | `validate` и прогон всех фикстур через настоящий pipeline агента, расчёт precision. **Эту команду запускает CI** |
| `sanitize --in <файл> --out <файл> [--grep <текст>] [--context 30]` | санитизированный фрагмент лога для фикстуры (см. раздел 7) |
| `corpus --kb kb --dir <каталог> [--examples 3] [--signature <ID>]` | отчёт о срабатываниях на ваших собственных логах (`.log`, `.log.gz`, `.txt`): так проверяют precision на реальных данных |

## 3. Формат сигнатуры

Файл: `kb/signatures/<категория>/<id>.yml`, имя файла должно совпадать с `id`. Пример — [`kb/signatures/database/SIG-DB-001.yml`](../kb/signatures/database/SIG-DB-001.yml), шаблон — [`templates/signature.yml`](templates/signature.yml).

| Поле | Обяз. | Правила |
|---|---|---|
| `id` | ✓ | `SIG-[A-Z]{2,4}-\d{3}`, уникален |
| `version` | ✓ | целое; увеличивайте при изменении логики или текста |
| `title` | ✓ | ≤ 256 символов |
| `category` | ✓ | ≤ 32 символов; сейчас используются `auth`, `database`, `disk`, `memory`, `network`, `performance`, `plugin`, `startup`, `velocity`, `world` |
| `severity` | ✓ | `info` \| `warning` \| `error` \| `critical`. У `error`/`critical` агент отправляет диагноз сразу |
| `scope` | | `server` (по умолчанию) или `network` |
| `platforms` | ✓ | список из `paper`, `purpur`, `velocity`; на других платформах сигнатура не проверяется. Первая платформа — платформа фикстур по умолчанию |
| `rule_ref` | | внутренний код правила Tickwise (≤ 16); сообщество его не заполняет, мейнтейнер добавит при необходимости |
| `symptoms` | ✓ | список строк |
| `match` | ✓ | дерево предикатов (§4); обязано содержать log-предикат как доказательство |
| `threshold` | | `{ count: N, window: <число><s\|m\|h\|d> }`: сколько совпадений за окно нужно для срабатывания. По умолчанию достаточно одного совпадения |
| `cause` | ✓ | основная причина, ≤ 8192 |
| `possible_causes` | | `[{ text, weight }]` |
| `fix` | ✓ | `instructions_md` (✓, Markdown, ≤ 8192; первая строка показывается в `/tickwise diagnose`), `risk` (`low` по умолчанию; используются `low`/`medium`/`high`), `action` — **обязательно `null`** (Tickwise не выполняет команды на серверах) |
| `confidence` | ✓ | число в (0, 1] |
| `verification` | ✓ | `verified` \| `community` \| `candidate`. **Новая сигнатура от сообщества — `candidate`**; уровень повышает мейнтейнер после ревью |
| `last_verified` | | дата |
| `sources` | ✓ | ссылки на первоисточники (исходники, issue, документация); в pack попадают как `references` |
| `tests` | ✓ | `positive: [...]`, `negative: [...]` — пути к фикстурам относительно `kb/`, внутри `kb/` |

YAML читается безопасным загрузчиком: дубликаты ключей запрещены, alias'ов не больше 10.

## 4. Предикаты `match`

У каждого узла ровно один ключ. Глубина вложенности не больше 8.

| Предикат | Параметры | Истинно, если |
|---|---|---|
| `log` | `regex` (✓, RE2, ≤ 2048), `literal` (подстрока-префильтр, ≤ 256), `level` (минимальный уровень), `target` (`message` \| `exception` \| `text`, по умолчанию `text`), `logger` (RE2 по имени логгера) | событие лога подходит |
| `all` | список | все дочерние истинны |
| `any` | список | хотя бы один дочерний истинен |
| `not` | предикат | дочерний ложен |
| `platform` | `name` (строка или список), `versions` (диапазон) | платформа и версия подходят; если версия неизвестна, `versions` не проверяется |
| `java` | `versions` (✓) | версия Java в диапазоне |
| `plugin` | `name` (✓), `versions`, `present` (по умолчанию `true`) | плагин установлен (и версия в диапазоне); при `present: false` — не установлен |
| `config` | `file`, `key`, `eq` | значение ключа равно `eq` без учёта регистра |

`target` у `log`:
- `message` — первая строка события;
- `exception` — строки цепочки исключения в виде `Class: message`;
- `text` — всё событие, включая фреймы stack trace.

`level` принимает `TRACE`, `DEBUG`, `INFO`, `WARN`/`WARNING`, `ERROR`/`SEVERE`, `FATAL`. Опечатка молча превращается в `INFO`. RE2 не поддерживает backreference и lookaround. Всегда задавайте `literal`: RE2 запускается только на строках, где найден литерал.

**Правило доказательства:** `match` должен «использовать лог». `all` — хотя бы один дочерний узел содержит `log`; `any` — **каждая** ветка содержит `log`; `not` доказательством не считается. Сигнатура без доказательства из лога не собирается.

**Ограничение `config`:** агент знает только значения ключей, которые есть в `kb/config-schema.yml` с `send: value` и не попадают под denylist секретов (в имени нет `pass|secret|token|key|webhook|rcon|auth|credential`). Для остальных ключей `config` всегда ложен.

Предикаты `platform`, `java`, `plugin`, `config` парсер поддерживает, но текущие сигнатуры их не используют. Предикат, которого агент не знает, делает сигнатуру невалидной для `kb-tools` (агент такую сигнатуру пропустил бы).

### Диапазоны версий

Сравнители через пробел или запятую работают как «И»: `>=1.21 <1.22`, `=26.2`, `>1.20.4`, `<=3.4`. Префикс: `1.21.x` или `1.21.*`. Любая версия: `*` или пусто. Сравнение идёт по числовым сегментам, суффиксы вроде `-SNAPSHOT` и `+build` игнорируются. Нераспознаваемая версия диапазону не удовлетворяет.

## 5. Фикстуры

Фикстура — текст лога в формате `latest.log` с необязательным заголовком. Заголовок — строки `# ключ: значение` в самом начале файла; он заканчивается на первой строке, которая не начинается с `# `.

```
# platform: velocity 3.5.1
# java: 21.0.4
# plugins: LuckPerms 5.5.17, Vault 1.7.3
# config: server.properties:online-mode=false
# expect: SIG-DB-002
# source: own-server-sanitized (прокси, 2026-09-20; хост БД заменён на db.example.net)
[09:20:00] [LuckPerms - Task Executor #34/ERROR] ...
```

| Ключ | Значение | По умолчанию |
|---|---|---|
| `platform` | `<имя> [версия]` | первая платформа сигнатуры; версия `1.21.11` (для `velocity` — `3.5.1`) |
| `java` | версия | `21.0.4` |
| `plugins` | `Имя версия, Имя версия` | нет плагинов |
| `config` | `<файл>:<ключ>=<значение>`; строк может быть несколько | нет |
| `expect` | ID других сигнатур, которые **законно** срабатывают на этой фикстуре (через запятую) | нет |
| `source` | происхождение: `synthetic`, `own-server-sanitized`, `upstream-issue <url>` и т.п. Не интерпретируется, но обязательно для ревью | — |

Раскладка: `kb/fixtures/<ID>/pos-<описание>.log` и `neg-<описание>.log`. Одна фикстура может быть позитивной для одной сигнатуры и негативной для другой.

Фикстуры проходят через тот же pipeline, что и в агенте: парсер, сборка stack trace, санитайзер с фиксированной солью, движок сигнатур. Поэтому регулярка должна совпадать с **санитизированным** текстом: ники, IP и хосты в нём уже заменены.

## 6. Требования к качеству (`kb-tools test`)

Тест проходит, только если выполнены все условия:

1. У каждой сигнатуры ≥ 3 позитивных и ≥ 3 негативных фикстур.
2. Каждая сигнатура срабатывает на всех своих позитивных фикстурах.
3. Ни одна сигнатура не срабатывает на своих негативных фикстурах.
4. Precision по всей базе ≥ 0.95. Истинное срабатывание — сигнатура сработала на своей позитивной фикстуре или на фикстуре, где она указана в `# expect:`. Ложное — сработала на любой другой фикстуре (`FALSE-POSITIVE` в выводе).
5. В базе не меньше 30 сигнатур (сейчас это условие выполняется).

Итог выводится строкой `signatures=… fixtures=… true_positives=… false_positives=… precision=…` и затем `KB TEST PASSED` или `KB TEST FAILED`.

Практика по негативным фикстурам: берите соседние сценарии, которые легко спутать с целевым (другая причина той же ошибки, штатные INFO-строки с тем же словом, соседний тип исключения). Именно они ловят слишком широкие регулярки.

## 7. Фикстуры из реальных логов

Допустимые источники: логи **ваших** серверов, публичные issue (с логами их авторов) и синтетика, собранная по настоящему формату сообщения. Логи чужого сервера без разрешения владельца присылать нельзя.

```bash
kb-tools sanitize --in /path/latest.log --out kb/fixtures/SIG-XX-000/pos-case.log --grep "Communications link failure" --context 30
```

- Сначала санитайзер проходит весь файл и «выучивает» ники из строк входа и выхода, затем пишет ±`context` строк вокруг первой строки с `--grep` (без `--grep` — весь файл).
- Соль фиксированная, поэтому псевдонимы воспроизводимы. Строки чата (`Async Chat Thread`, `<ник> …`) удаляются.
- Режим каталога: `--in <каталог> --out <каталог>` обрабатывает все `.log`/`.gz` с общим словарём ников.
- **Обязательно прочитайте результат построчно** перед коммитом: хосты БД, домены, пути, названия проектов замените на `example`-значения, как в существующих фикстурах (подробнее — [раздел 4 в CONTRIBUTING.ru.md](../CONTRIBUTING.ru.md#4-настоящие-логи-и-приватность)).
- Добавьте заголовок (`# platform`, `# source` и др.) вручную: `sanitize` его не пишет.
- CI дополнительно запускает `scripts/lint-fixtures.sh`: он ловит похожие на настоящие IP-адреса, e-mail и секреты. Это страховка, а не замена вашему чтению.

## 8. Уровни доверия (`verification`)

| Уровень | Что означает | Кто ставит |
|---|---|---|
| `candidate` | гипотеза или новая сигнатура. Её фикстуры проверяются в CI, но **в подписанный pack она не входит** и до пользователей не доходит | автор вклада |
| `community` | принята после ревью, причина подтверждена источниками, но позитивные фикстуры могут быть синтетическими | мейнтейнер |
| `verified` | подтверждена на реальных логах и первоисточниках | мейнтейнер |

Для `candidate` валидатор требует: у каждого `log`-предиката `literal` не короче 8 символов, а якорем служит `target: exception`, предикат `plugin` или `literal` не короче 16 символов. `verified` не может опираться на позитивные фикстуры с `synthetic` в имени файла.
